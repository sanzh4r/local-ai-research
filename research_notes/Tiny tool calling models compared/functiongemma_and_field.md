## 1. FunctionGemma: what it is, format, size, fine-tuning story, licence, runtimes, successor, hackathon

### Takeaway
FunctionGemma is Gemma 3 270M re-trained by Google for text-only function calling with its own control-token chat format; Google itself says it is a base to be fine-tuned, not a finished product (58% -> 85% on its own Mobile Actions eval). It is roughly 240-290 MB on disk and about 550 MB peak RAM, an order of magnitude larger than Needle, and as of Nov 2026 Google has published no "FunctionGemma 2"; Gemma 4 (Apr 2026) has native function calling but its smallest model is ~2.3B effective parameters.

### Cited Findings

**Identity, base, architecture**
- "Built on the Gemma 3 270M model ... FunctionGemma has been trained specifically for function calling. The model has the same architecture as Gemma 3, but uses a different chat format." Text-only. Authors: Google DeepMind. [C][D] — [FunctionGemma model card (Unsloth mirror)](https://huggingface.co/unsloth/functiongemma-270m-it)
- Context: 32K tokens total input; output up to 32K minus input. [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
- Trained with 6T tokens (same figure the Gemma 3 card gives for the 270M base); knowledge cutoff August 2024. Function-calling data components: "Public Tool Definitions - Common APIs found on the web" and "Tool Use Interactions" (prompts, function calls, function responses, natural-language summaries, and clarification requests when the prompt is ambiguous or incomplete). [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it); base figure: [Gemma 3 270M card mirror](https://huggingface.co/unsloth/gemma-3-270m-it)
- Public release: 18 Dec 2025 (HN submission "FunctionGemma 270M Model" timestamped 2025-12-18, 226 points, 56 comments). The HF repo itself was created 2025-10-08 (pre-staged). [I][D] — [HN thread](https://news.ycombinator.com/item?id=46316533); [HF API listing](https://huggingface.co/api/models?search=functiongemma&author=google)
- Not multimodal: in the voice demos "a separate model is performing ASR"; "Gemma270m (base, function, and others) are not multimodal out of the box" (commenter identifying as research lead on the model). No thinking mode by design: "we actually did not include thinking into this model partly because we saw how incredibly fast it was to just get the minimum amount of tokens". [C][D] — [HN thread](https://news.ycombinator.com/item?id=46316533)

**Function-calling format**
- Tools are declared as ordinary JSON-schema function objects and passed through the chat template (`apply_chat_template(message, tools=[...])`); the template serialises them into the prompt. [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
- A `developer` role turn is required: "ESSENTIAL SYSTEM PROMPT: This line activates the model's function calling logic" with content "You are a model that can do function calling with the following functions". [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
- Output is not JSON. Card example: `<start_function_call>call:get_current_temperature{location:<escape>London<escape>}<end_function_call>` i.e. control tokens delimit the call, and string values are wrapped in `<escape>` tokens. The model "will then generate one or more function calls". [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
- A third-party blog states Gemma 4 E2B uses "the same special-token vocabulary for function calls that FunctionGemma uses". [I][S] — [ertas.ai blog](https://www.ertas.ai/blog/agent-specialists-functiongemma-gemma4-e2b-fine-tuning)

**Size on disk and RAM, speed**
- Google's on-device test (Samsung S25 Ultra, CPU, LiteRT XNNPACK, 4 threads, dynamic_int8, context 1024; 512 prefill + 32 decode tokens): Mobile Actions fine-tune 288 MB model size, 551 MB peak RSS, 1718 tok/s prefill, 125.9 tok/s decode, 0.3 s time-to-first-token. Tiny Garden fine-tune: 288 MB, 549 MB peak RSS, 1743 / 125.7 tok/s, 0.3 s. [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
- GGUF file sizes (Unsloth repo): BF16 542.8 MB; Q8_0 291.6 MB; Q4_K_M 253.1 MB; Q4_0 241.6 MB; Q2_K 237.1 MB; smallest "UD-IQ2_XXS" 179.7 MB. [I][D] — [HF file tree API](https://huggingface.co/api/models/unsloth/functiongemma-270m-it-GGUF/tree/main)
- Cactus claims FunctionGemma runs "at up to 3000 toks/sec prefill speed on M4 Macs" and "decode speed reaches 200 tokens/sec, all without GPU". [C: Cactus][D] — [hackathon README](https://raw.githubusercontent.com/cactus-compute/functiongemma-hackathon/main/README.md)
- Independent CPU laptop test via Ollama (Framework 13, Ryzen AI 7 350, no GPU): FunctionGemma averaged 435 ms per prompt, fastest of 21 models. [I][D] — [Local Agent Bench README](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md)

**Google's own accuracy numbers (zero-shot)**
- BFCL sub-scores, 0-shot, from the card: Simple 61.6; Multiple 63.5; Parallel 39; Parallel Multiple 29.5; Live Simple 36.2; Live Multiple 25.7; Live Parallel 22.9; Live Parallel Multiple 20.8; Relevance 61.1; Irrelevance 73.7. No overall BFCL score and no multi-turn score is given. [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)

**"Must be fine-tuned" guidance**
- Card note: "FunctionGemma is intended to be fine-tuned for your specific function-calling task, including multi-turn use cases." Also: "not intended for use as a direct dialogue model, and is designed to be highly performant after further fine-tuning, as is typical of models this size." [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
- Research lead on HN: "these size models perform best for specific users when finetuned to that specific use case"; composing calls (feeding one result into another) "saw some promise but didn't heavily train for this use case in the base model". Two fine-tuning modes described: "obliterate any general functionality" vs preserve generality with low learning rate or LoRA. [C][D] — [HN thread](https://news.ycombinator.com/item?id=46316533)

**Mobile Actions dataset and recipe**
- Card table: base FunctionGemma 58% -> "Mobile Actions Fine-Tune" 85% on the Mobile Actions eval. [C][D] — [model card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
- Google's blog phrases it as "boosting accuracy from a 58% baseline to 85%"; the DeepMind page shows the same chart. [C][S] — [blog.google](https://blog.google/technology/developers/functiongemma/); [deepmind.google](https://deepmind.google/models/gemma/functiongemma/)
- Dataset `google/mobile-actions`: licence CC-BY-4.0; JSONL; each sample has `metadata` ("train" or "eval"), `tools` (name, description, JSON-schema-like parameters), `messages` with expected `tool_calls`; described as "conversational traces designed to train lightweight models (such as FunctionGemma 270M) to translate natural language instructions into executable function calls for Android OS system tools". [C][D] — [dataset card](https://huggingface.co/datasets/google/mobile-actions/raw/main/README.md)
- Dataset is about 9,600 samples. [I][S] — [SimpleTool paper, arXiv 2603.00030](https://arxiv.org/abs/2603.00030)
- Recipe: fine-tune with Hugging Face TRL, convert and quantize to `.litertlm` for LiteRT-LM, load into the Google AI Edge Gallery "Mobile Actions" task. Each sample includes a system prompt with context such as current date and time. [C][S] — [ai.google.dev Mobile Actions guide](https://ai.google.dev/gemma/docs/mobile-actions)
- A Hugging Face demo notes exact-match accuracy is a lower bound (an equivalent but reworded argument counts as wrong). [I][S] — [HF Space](https://rlkit-train-mobile-controller-llm.hf.space/)

**Independent replications of the before/after gap**
- arXiv 2609.25373 (21 Sep 2026), "Extending FunctionGemma for Practical On-Device Mobile Function Calling": new synthetic dataset of ~9,500 conversations over 15 device-control categories. On it, base FunctionGemma scores 29.3%, Google's Mobile-Actions specialist 17.2%, their fine-tune 76.5%. Google's specialist scores 90.3% on Google's own Mobile Actions set; a combined model gets 82.3% there (an 8.0-point trade for doubled category coverage). [I][D abstract only] — [arXiv 2609.25373](https://arxiv.org/abs/2609.25373)
- distil-labs home-assistant fine-tune (multi-turn, 6 tools, distilled from a 120B teacher): FunctionGemma base 38.82% tool-call accuracy -> 96.71% tuned; teacher 92.11%. [C: distil-labs][D] — [model card](https://huggingface.co/distil-labs/distil-home-assistant-functiongemma)
- SimpleTool (4 Feb 2026): abstract says "On Mobile Actions, ST-Qwen-0.5B outperforms Google's FunctionGemma in both accuracy and latency consistency" [I][D]; numbers 69.3% zero-shot vs 58%, 86.2% fine-tuned vs 85.0%, P50 51.0 ms vs 61.1 ms come from a search summary only [S]. — [arXiv 2603.00030](https://arxiv.org/abs/2603.00030)

### Inferences
- 4-bit quantisation barely shrinks the file (Q8 292 MB vs Q4_K_M 253 MB vs BF16 543 MB), which is what you would expect if most parameters sit in a large token-embedding table that quantisers leave at higher precision. Practical floor for FunctionGemma is about 180-290 MB on disk and about 0.55 GB RAM: 6-20x Needle's 14-29 MB.
- The hackathon is itself evidence about FunctionGemma: Cactus and Google chose to frame the event around when to *escalate away* from the 270M model, and built a hidden eval that is "quite difficult for FunctionGemma by design". Cactus later shipped its own much smaller model (Needle), which reads as a response to what the hackathon exposed, though I found no source stating that causally.
- The arXiv 2609.25373 result (Google's Mobile Actions specialist drops to 17.2% on neighbouring phone categories, below the un-tuned base's 29.3%) shows fine-tuned 270M specialists are narrow: fine-tuning buys accuracy on the trained tool set and costs generality outside it.
- 85% is Google's headline "after" number, but independent tuners report both higher (90.3% for Google's own specialist as re-measured; 96.7% distil-labs on 6 tools) and that everything depends on tool-set size and eval strictness. These numbers are not comparable across papers.
- No FunctionGemma 2 after 11 months, while Gemma 4 E2B carries native function calling, suggests Google's direction is "bigger general on-device model with tool calling" (Gemini Nano 4 path) with FunctionGemma 270M kept alive as the tiny fine-tunable option.

### Gaps

Check [ai.google.dev/gemma/docs/functiongemma](https://ai.google.dev/gemma/docs/functiongemma).
- Parameter split of Gemma 3 270M (commonly described as ~170M embedding + ~100M transformer) was not verified in a source this session.
- Fine-tuning recipe hyperparameters (epochs, LR, LoRA vs full) and the exact train/eval split sizes of Mobile Actions: notebook on GitHub not accessible.
- Official hackathon winners and final leaderboard: not found.
- Whether Google has announced a Gemma 4-based FunctionGemma: no evidence found; absence is based on the HF listing and one search, not on an explicit Google statement.

## 2. Other contenders: size, licence, tool-call approach, reported accuracy

### Takeaway
Outside Needle and Liquid, the sub-1B field is thin: FunctionGemma (270M), Qwen3-0.6B / Qwen3.5-0.8B (general models with trained-in tool calling, Apache 2.0), Hammer 2.1-0.5B (fine-tuned specialist, non-commercial), and the older sub-1B Octopus v3. Most "small function-calling" names people cite (xLAM-1b, Arch-Function-1.5B, TinyAgent-1.1B, Octopus v2, SmolLM3, Phi-4-mini, Gemma 4 E2B, Apple's on-device model) are 1-4B, i.e. a different weight class.

**Apple (OS-bundled, not a downloadable model)**
- Foundation Models framework: Apple's docs describe `Tool` as a protocol for code the model can call "to gather runtime information or perform side effects"; the framework "puts the tool definitions — name, description, parameter information — in the prompt"; tool output is typically a String or a `Generable` type. `@Generable` / `@Guide` give typed, constrained structured output. [C][S] — [Apple Tool docs](https://developer.apple.com/documentation/foundationmodels/tool.md)
- Third-party guides: iOS 26 ships a ~3-billion-parameter on-device model; requires an Apple-Intelligence-capable device. [I][S] — [blakecrosley.com guide](https://blakecrosley.com/blog/apple-foundation-models-framework); [createwithswift](https://createwithswift.com/exploring-the-foundation-models-framework/)
- WWDC 2026 (June 2026): Apple said a new on-device model is "rebuilt from the ground up ... better at logic and tool calling"; additions reported include image input, Private Cloud Compute server-side intelligence, dynamic sessions, and a `LanguageModel` protocol for third-party cloud providers. [C via press][S] — [implicator.ai](https://www.implicator.ai/apple-expands-xcode-and-foundation-models-for-wwdc-ai-developers/); [MacRumors](https://macrumors.com/2026/06/09/apple-outlines-major-ai-and-developer-tool-updates)
- Core AI: announced at WWDC26 as successor to Core ML, "a brand new framework for running custom on-device models, with ahead-of-time compilation, dedicated instruments, and Python tools for converting PyTorch models to Apple silicon". - Sources conflict on language counts (15, 24, 25) and on model naming/size ("AFM 3 Core", ~3B appears in one blog only). [I][S] — same search set; see [dev.to summary](https://dev.to/hariharanjagan/whats-new-in-apples-foundation-models-framework-at-wwdc-2026-5227)

**2026 newcomers and adjacent work**
- SimpleTool (Feb 2026): special tokens compress low-entropy output tokens 4-6x and let function name and arguments decode in parallel; 3-6x end-to-end speedup; evaluated on Qwen models 0.5B-14B; ST-Qwen-0.5B claimed better than FunctionGemma on Mobile Actions. [C][D abstract] — [arXiv 2603.00030](https://arxiv.org/abs/2603.00030)
- Needle2 "Show HN: Needle2: 14MB agentic LLM for phones, wearables, smart home and robots", 10 Aug 2026, 537 points (covered by another researcher; listed here only as the field's main 2026 entrant). [I][D] — [HN](https://news.ycombinator.com/item?id=49246804)

[I][D] — [HF API listing](https://huggingface.co/api/models?search=functiongemma&sort=downloads&limit=15)
- A 2026 small-model guide lists the under-1.5B tier as Qwen3.5-0.8B, Llama 3.2 1B, LFM2.5-1.2B. [I][S] — [vdf.ai](https://vdf.ai/blog/best-small-language-models/)

### Inferences
- Licence is a real differentiator: Qwen (Apache 2.0), SmolLM (Apache 2.0), Gemma 4 (Apache 2.0), Phi and TinyAgent (MIT) are commercially clean; FunctionGemma carries Google's custom Gemma terms; Hammer, xLAM and Octopus v2 are CC-BY-NC (research/non-commercial), and Arch-Function has a bespoke research licence. Several of the best-known "function-calling specialists" therefore cannot simply be shipped in a product.
- Apple is a different kind of competitor: zero download size for the developer, typed Swift API with constrained output, but Apple-only, limited to recent hardware, and around 3B parameters, so it competes on convenience, not on footprint. A 14-29 MB model can run on watches, microcontrollers and Android; Apple's model cannot be moved.
- The fine-tuned 0.5-1.5B specialists of 2024 (Hammer, xLAM, Arch) have not been refreshed in 2025-26 as far as HF dates show (latest: xLAM-2 Mar 2025), while general small models (Qwen3, Qwen3.5, Gemma 4, SmolLM3) absorbed tool calling into base training. The specialist niche has moved downward in size (FunctionGemma 270M, Needle 26-121M).

### Gaps
- Hammer 2.1-0.5B, xLAM-2-1b and Arch-Function BFCL numbers are published only as images; I could not read values.
- Qwen3.5-0.8B BFCL-V4 column mapping needs confirmation against the rendered card.
- Apple: context-window size of the on-device model, exact parameter count, and any Apple-published tool-calling accuracy were not confirmed (a search specifically for the 4,096-token figure returned no source). No independent tool-calling benchmark of Apple's on-device model was found.
- Microsoft "Phi small" below 1B: I found no sub-1B Phi with tool calling; Phi-4-mini (3.8B) is the smallest verified.
- Octopus v3 licence and public weights availability not verified.
- Any Gemma 4 model below E2B: none on the card; not found.

## 3. Design approaches and their trade-offs

### Takeaway
There are five recognisable designs, ordered roughly from most general/largest to most specialised/smallest; each step down buys size and latency and pays in generality, multi-step ability, and the need for per-application training.

### Cited Findings
- **(a) General small LLM + prompt/template.** Qwen3-0.6B, Qwen3.5-0.8B, SmolLM3, Phi-4-mini, Gemma 4 E2B. Tools are JSON pasted into the prompt via the chat template; the model emits JSON in tags. Example formats: SmolLM3 `<tool_call>{"name":...}</tool_call>`; Phi-4-mini tools wrapped in `<|tool|>...<|/tool|>`. [C][D] — [SmolLM3 card](https://huggingface.co/HuggingFaceTB/SmolLM3-3B); [Phi-4-mini card](https://huggingface.co/microsoft/Phi-4-mini-instruct). Independent evidence it can work at 0.6B: qwen3:0.6b scored 0.880 Agent Score vs FunctionGemma 0.640, but took 3,410 ms vs 435 ms on CPU. [I][D] — [Local Agent Bench](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md)
- **(b) Fine-tuned function-calling LLM (format baked in).** FunctionGemma, Hammer, xLAM, Arch-Function. FunctionGemma: dedicated control tokens, no thinking, meant to be fine-tuned again per app. [C][D] — [FunctionGemma card mirror](https://huggingface.co/unsloth/functiongemma-270m-it). Hammer's paper identifies the characteristic weakness of this class: performance "varies significantly across benchmarks, often due to being misled by specific naming conventions", addressed with function masking and irrelevance-augmented data. [C][D] — [arXiv 2410.04587](https://arxiv.org/abs/2410.04587)
- **(c) Functional-token / classification approach.** Octopus v2 maps each function to a dedicated new token, so choosing a function is a single-token classification and function descriptions need not be in the prompt: "decrease the context length by 95%", 0.38 s latency, 98-100% on its own benchmark; contrasted with RAG methods needing "tens of thousands of input tokens". [C][D] — [arXiv 2404.01744](https://arxiv.org/abs/2404.01744); [card](https://huggingface.co/NexaAIDev/Octopus-v2). Nexa calls the technology "patented". [C][D] — [card](https://huggingface.co/NexaAIDev/Octopus-v2). SimpleTool (2026) is a related idea: special tokens as compression and as mode selectors for parallel decoding of name and arguments. [C][D] — [arXiv 2603.00030](https://arxiv.org/abs/2603.00030)
- **(d) Planner + tool retrieval.** TinyAgent: fine-tuned 1.1B planner (LLMCompiler) plus "a novel tool retrieval method to reduce the input prompt length" and quantisation. [C][D] — [arXiv 2409.00608](https://arxiv.org/abs/2409.00608)
- **(e) Ultra-tiny distilled specialist / single-pass decision models.** Needle (14 MB) and Liquid's decision models are covered by other researchers. Evidence on the trade-off from the Needle2 launch thread: the Cactus author says "its not a generalist model ... Needle is niche, not a Gemma or GPT replacement", exposes a confidence score ("around +60% confidence threshold is cool from experiments ... you gotta test on your own workload, no existing benchmark could honestly paint the full picture"), and ships pipelines to "synthesize augmentations and fine-tune on your samples". [C][D] — [HN Needle2 thread](https://news.ycombinator.com/item?id=49246804)
- **Hybrid edge/cloud routing as a pattern on top of (b)/(e).** The Feb 2026 hackathon task was the router itself (confidence algorithms, prompt and tool-description patterns). [C][D] — [hackathon README](https://raw.githubusercontent.com/cactus-compute/functiongemma-hackathon/main/README.md). In the launch thread a commenter asked whether Google evaluates the "call a (wiser) friend" strategy; the research lead answered in general terms without citing a benchmark. [I/C][D] — [HN thread](https://news.ycombinator.com/item?id=46316533)
- **Reliability add-ons.** HN commenters proposed majority-vote/quorum sampling to push 85% higher; a reply noted this "works only if the fails are roughly independent. More important is the complexity ceiling above which they fail all the time." [I][D] — [HN thread](https://news.ycombinator.com/item?id=46316533). ToolRM paper: best-of-n sampling with Qwen3-0.6B plus a 14B reward-model ranker lifted accuracy from 39.5% to 64.38% on non-BFCL benchmarks. [C][S] — [arXiv 2509.11963](https://arxiv.org/pdf/2509.11963)
- **Constrained decoding (OS-level).** Apple's `@Generable` returns a populated, type-checked Swift value instead of text to parse. [C][S] — [Apple docs](https://developer.apple.com/documentation/foundationmodels/tool.md)

### Inferences
Trade-off summary for a non-specialist (my synthesis of the above):

| Approach | What you ship | Strength | Weakness |
|---|---|---|---|
| (a) General small LLM + prompt | 0.4-3 GB model, tool JSON in prompt | Works with new tools without retraining; can chat, reason, sometimes think; permissive licences | Prompt grows with every tool (latency, context); slowest; format errors unless the runtime's parser matches |
| (b) Fine-tuned FC LLM | 0.25-1.5 GB | Reliable syntax; faster; can still read unseen tool descriptions somewhat | Zero-shot accuracy mediocre at 270M (58%, 29%, 39% in three evals); needs per-app fine-tune; fine-tune narrows it |
| (c) Functional tokens | model with N extra tokens | Shortest prompt, one-token function choice, very fast, very high in-domain accuracy | Tool set is frozen into the weights; adding a tool means retraining; numbers are self-benchmarked; patent/NC licence |
| (d) Planner + tool retrieval | small LLM + retriever | Handles larger tool catalogues and multi-step plans | More moving parts; retrieval misses become silent failures |
| (e) Ultra-tiny specialist / decision model | 14-30 MB (Needle) | Runs on MCUs, watches, browsers; near-zero latency and energy; confidence output enables routing | No general reasoning (relative values, units, implicit intent); must be tuned per workload; needs a fallback |

- Constrained decoding and confidence thresholds address different failures: constraints guarantee *well-formed* calls, they do not make the *choice* of tool or the *value* of an argument right. The independent bench's conclusion ("The hard problem isn't generating well-formed JSON. It's deciding whether to act at all") supports this.
- The smaller the model, the more the system design (router, fallback, validation, enums in schemas, relative-vs-absolute tool design) matters relative to the model.

### Gaps
- No source found that compares all five approaches on one benchmark under one protocol.
- No published evaluation of a "small model escalates to large model" calibration benchmark (the HN question went unanswered with data).

## 4. Benchmarks used in this niche

### Takeaway
BFCL is the common yardstick but its versions measure different things, and almost no sub-1B model has a full, current, independently run BFCL score; most headline numbers in this niche come from the vendor's own small, single-turn, in-domain test set (Mobile Actions, Octopus's Android set, TinyAgent's macOS set), so cross-model comparison is weak.

### Cited Findings
- **BFCL v1 (Berkeley Function Calling Leaderboard, 2024).** Single-turn categories simple / multiple / parallel / parallel-multiple, plus relevance detection, across Python, Java, JavaScript; AST matching and executable checks. xLAM's card describes it as covering "various programming languages and application domains like Java, JavaScript, and Python". [C][D] — [xLAM-1b card](https://huggingface.co/Salesforce/xLAM-1b-fc-r). (Related paper fetched but not parsed: [arXiv 2402.15491](https://arxiv.org/abs/2402.15491).)
- **BFCL v2 "Live".** FunctionGemma's card reports separate "Live Simple / Live Multiple / Live Parallel / Live Parallel Multiple" rows, markedly lower than the non-live rows (36.2 vs 61.6 on Simple). [C][D] — [FunctionGemma card mirror](https://huggingface.co/unsloth/functiongemma-270m-it). The Arch-Function card's table layout shows the v3-era columns: Overall; Single Turn Non-live (AST), Non-live (Exec), Live (AST); Multi Turn; Hallucination Relevance / Irrelevance. [C][D] — [Arch-Function card](https://huggingface.co/katanemo/Arch-Function-1.5B)
- **BFCL v3 (multi-turn).** "BFCL V3 introduced multi-turn and multi-step function calling that let models interact with the user", including clarification. [C: Berkeley][S] — [Gorilla blog index](https://gorilla.cs.berkeley.edu/blogs/15_bfcl_v4_web_search.html). Even GPT-4o (FC) scored only 62.19% overall and 25.00% multi-turn as of 21 Oct 2024. [C][D] — [Arch-Function card](https://huggingface.co/katanemo/Arch-Function-1.5B)
- **BFCL v4 (agentic, 2025).** Adds web search (100 human-crafted multi-hop questions, DuckDuckGo search tool), memory (key-value store, vector store, recursive summarisation back-ends), and a format-sensitivity study (Python vs JSON calls, Python vs XML function docs). [C: Berkeley][S] — [web search blog](https://gorilla.cs.berkeley.edu/blogs/15_bfcl_v4_web_search.html); [memory blog](https://gorilla.cs.berkeley.edu/blogs/16_bfcl_v4_memory.html); [format blog](https://gorilla.cs.berkeley.edu/blogs/17_bfcl_v4_prompt_variation.html). A third-party guide says the v4 overall weights agentic 40% and multi-turn 30%, with format sensitivity unscored; unconfirmed against Berkeley. [I][S] — [bfcl guide](https://jonathanding.github.io/llm-learning/en/articles/bfcl-guide)
- **Published BFCL numbers for small models.**
  - FunctionGemma 270M: sub-scores only (Simple 61.6, Multiple 63.5, Parallel 39, Parallel Multiple 29.5, Live rows 20.8-36.2, Relevance 61.1, Irrelevance 73.7). [C][D] — [card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
  - xLAM-1b-fc-r (1.35B): 78.94% overall on the Jul 2024 leaderboard, "the only tiny model with less than 2B parameters on the leaderboard". [C][D] — [card](https://huggingface.co/Salesforce/xLAM-1b-fc-r)
  - Llama 3.2 1B 10.82% and Llama 3.2 3B 21.95% on the official leaderboard as last updated 12 Apr 2026; the leaderboard "does not yet list the 2026 small models". [I][S] — [vdf.ai](https://vdf.ai/blog/best-small-language-models/)
  - Qwen3.5-0.8B card BFCL-V4 row: 25.3 (column mapping unconfirmed). [C][D] — [card](https://huggingface.co/Qwen/Qwen3.5-0.8B)
  - SmolLM3-3B "BFCL" 92.3; Qwen3-1.7B 89.5; Qwen3-4B 95.0 (version/subset not stated; clearly not the v3/v4 overall metric, on which GPT-4o scored 62%). [C][D] — [SmolLM3 card](https://huggingface.co/HuggingFaceTB/SmolLM3-3B)
- **Mobile Actions (Google, Dec 2025).** ~9,600 samples of Android system-tool commands with a train/eval split, CC-BY-4.0, synthetic-looking per an HN commenter. Scores: FunctionGemma base 58%, fine-tuned 85% (Google); Google's specialist re-measured at 90.3% (arXiv 2609.25373); ST-Qwen-0.5B 69.3% zero-shot / 86.2% tuned (search summary). [C][D] — [dataset card](https://huggingface.co/datasets/google/mobile-actions/raw/main/README.md); [card mirror](https://huggingface.co/unsloth/functiongemma-270m-it); [I][D] [arXiv 2609.25373](https://arxiv.org/abs/2609.25373); [S] [arXiv 2603.00030](https://arxiv.org/abs/2603.00030); HN comment [I][D] [thread](https://news.ycombinator.com/item?id=46316533)
- **tau-bench / TAU2-Bench.** Used by Salesforce for xLAM-2 as the "agentic" complement to BFCL v3, with training data from "simulated agent-human interactions"; Qwen3.5 card reports a TAU2-Bench row. Measures multi-turn task completion with a simulated user rather than single call correctness. [C][D] — [xLAM-2 card](https://huggingface.co/Salesforce/xLAM-2-1b-fc-r); [Qwen3.5-0.8B card](https://huggingface.co/Qwen/Qwen3.5-0.8B)
- **Self-made benchmarks.** Octopus v2: own Android API set, 99.5% (self) vs Phi-3 45.7%, "manually verified" spreadsheet. TinyAgent: own macOS 16-function task. Cactus hackathon: "hidden Cactus eval, quite difficult for FunctionGemma by design". [C][D] — [Octopus card](https://huggingface.co/NexaAIDev/Octopus-v2); [TinyAgent abstract](https://arxiv.org/abs/2409.00608); [hackathon README](https://raw.githubusercontent.com/cactus-compute/functiongemma-hackathon/main/README.md)
- **Home Assistant datasets/leaderboard** (`allenporter/home-assistant-datasets`, `acon96/Home-Assistant-Requests`, 32k+ examples) are the community's practical smart-home benchmark. [I][D] — [HN thread](https://news.ycombinator.com/item?id=46316533)
- **Local Agent Bench (Feb 2026, independent).** 12 prompts, 3 tools, 21 models, 20 runs each, CPU-only; scores Action, Restraint, Wrong-Tool, combined Agent Score = Action x 0.4 + Restraint x 0.3 + Wrong-Tool-Avoidance x 0.3. Author's own caveat: 3-run results were "a small-sample artifact" (qwen3:1.7b moved 0.670 -> 0.960, bitnet 0.810 -> 0.530 at 20 runs); Ollama returns only the first tool call so multi-tool is N/A for native-tools models; Ollama default 4,096-token context. [I][D] — [README](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md)
- **Known weaknesses, as stated by sources.**
  - Benchmark-specific overfitting: function-calling models' "performance varies significantly across benchmarks, often due to being misled by specific naming conventions". [C][D] — [Hammer paper](https://arxiv.org/abs/2410.04587)
  - Existing resources "emphasize web APIs or narrow mobile-action catalogs". [I][D] — [arXiv 2609.25373](https://arxiv.org/abs/2609.25373)
  - Exact-match scoring undercounts equivalent arguments. [I][S] — [HF Space](https://rlkit-train-mobile-controller-llm.hf.space/)
  - "Format compliance masks true behavior — in both directions": parser fixes for 5 models changed their scores. [I][D] — [Local Agent Bench](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md)
  - Vendor view: "no existing benchmark could honestly paint the full picture" (Cactus author). HN user objection: a demo "doesn't help me determine how well the model does across a decently-large sample size of commands". [C / I][D] — [Needle2 thread](https://news.ycombinator.com/item?id=49246804)
  - Aggregator tables for BFCL v4 disagree with each other (e.g. one guide's figures "don't match the other sources"). [I][S] — [spheron guide](https://www.spheron.network/blog/tool-calling-benchmarks-bfcl-tau-bench-latency-optimization/)

### Inferences
- "BFCL score" without a version is nearly meaningless: v1-era overall scores were 80-90% for good models (xLAM-7b 88.24%), v3 overall is ~60% for GPT-4o, and v4 is dominated by web-search and memory tasks that a 270M model with no reasoning cannot attempt. SmolLM3's 92.3 and Qwen3.5-0.8B's 25.3 are both "BFCL" but not comparable.
- For sub-1B models, the relevant BFCL slices are the single-turn AST categories and relevance/irrelevance; FunctionGemma's profile (60s on simple/multiple, 20-39 on parallel and live) shows the cliff: one obvious call from a few tools is fine, several calls or realistic user-written tool specs are not.
- Mobile Actions' 58 -> 85 is an in-distribution number (train and eval drawn from the same synthetic generator and the same handful of Android tools). The 17.2% out-of-category figure is the more honest indicator of what a tuned 270M does off its training distribution.
- Nearly every number in this niche is single-turn. Multi-turn (BFCL v3, tau-bench) results for sub-1B models are essentially unpublished.

### Gaps
- Nexus (Nexusflow/NexusRaven benchmark), ToolBench and API-Bank: I did not retrieve sources this session describing them or giving sub-1B scores; Hammer's "other academic benchmarks" figure (an image) likely includes some of them. From background knowledge only (unsourced here): API-Bank and ToolBench are 2023 academic suites of API-call dialogues / RapidAPI tool-use trajectories, and Nexus is Nexusflow's function-calling set; all predate the sub-1B wave and are rarely reported for these models.
- Official BFCL leaderboard page could not be opened; no first-hand confirmation of which sub-1B models are listed or of v4 weightings.
- No published criticism piece specific to BFCL v4 surfaced in search.
- BFCL overall / multi-turn scores for FunctionGemma, Qwen3-0.6B, Hammer-0.5B under one harness: not found.

## 5. Independent evaluations and community experience: where sub-1B tool calling fails

### Takeaway
Independent testing agrees with the vendors' fine print: sub-1B models handle clear, single, in-domain commands quickly, and fail on judgment (keyword traps, negation, already-supplied information), relative or unit-bearing arguments, multi-call requests, and anything outside the fine-tuned tool set. FunctionGemma specifically is the fastest and has good restraint but picks wrong tools on hard prompts, scoring below the general-purpose Qwen3-0.6B.

### Cited Findings
- **Local Agent Bench, round 3 (Feb 2026).** FunctionGemma: Action 0.600, Restraint 1.000, Wrong Tool 2 (of 3 trap prompts), Agent Score 0.640, 435 ms; tied with qwen2.5:0.5b and smollm2:1.7b at rank 11 of 21. qwen3:0.6b: 0.700 / 1.000 / 0 wrong / 0.880 at 3,410 ms (rank 3). lfm2.5:1.2b 0.920 at 1,567 ms; qwen3:1.7b 0.960 at 10,665 ms; llama3.2:1b last at 0.430 with 3 wrong tools. [I][D] — [README](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md)
- Author's conclusions: "Purpose-built doesn't mean best. functiongemma (270M, fine-tuned for function calling) is the fastest model ... with perfect restraint, but falls into the same keyword traps as generic models on hard prompts." "For routing clear-cut requests: Almost any functional model works. functiongemma does it at 435ms. The problem is solved." "For latency-critical deployments under 1 second: functiongemma (435ms, 0.640) and qwen2.5:0.5b (1,015ms, 0.640) are the only options. Both fail on judgment traps." "Parameter count is a weak predictor." "When prompts require judgment — resisting keyword triggers, respecting negation, noticing redundant information — most sub-4B models fail." [I][D] — [README](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md)
- The trap prompts, as concrete failure archetypes: P10 "meeting in Bruges next Thursday, train or cycle?" (right tool is weather, not schedule); P11 "Don't check the weather in Antwerp, just find me the quarterly report" (negation); P12 weather already given in the prompt (redundant call). P12 was passed reliably only by qwen3:1.7b. [I][D] — [README](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md)
- The benchmark's first write-up "went viral on r/LocalLLaMA"; commenters requested FunctionGemma, two predicting "very high performance per compute". Liquid's CEO amplified the round-2 result on X. [I][D for README; S for X] — [README](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md); [X post](https://x.com/ramin_m_h/status/2022896926371311836)
- **HN launch thread (18 Dec 2025).** Sceptical comment: "I would be wary of having a LLM with 85% accuracy call tools on my system. Isn't that fairly far away from production-grade performance? I also don't see that the fact that accuracy can be boosted from 50% to 85% is any indication that it can be boosted further." Another: for tasks that need the internet anyway, "there's no reason not to use cloud-hosted model which would work magnitudes better". Google team replies: complicated APIs "might need" fine-tuning; "better tool descriptions help"; 32K context is a hard limit for large tool results. [I and C][D] — [HN thread](https://news.ycombinator.com/item?id=46316533)
- **Argument errors on ultra-tiny models (Needle2 Show HN, 10 Aug 2026)**, illustrative of the class:
  - "Make it a little warmer in here" -> `set_thermostat` temperature 65, mode "cool", with reasoning "'warmer' implies need for cooling".
  - "5° warmer" -> set temperature to 5°F (relative vs absolute). A commenter: "models of this size can't reason about relative values very well. Give it a tool to change temperature by a given amount".
  - Units: with the parameter described as "degrees Fahrenheit", "Set the living room temperature to 70 degrees Celsius" still yields temperature 70 (confidence 0.6045): "Specifying units seems to be unreliable".
  - A navigation/path-planner prompt failed twice.
  - User preference: if failures are unpredictable, "I'd prefer the dumb old 'I did not understand that' response". Vendor reply: confidence output exists for exactly this; fine-tune on your own samples.
  [I and C][D] — [HN Needle2 thread](https://news.ycombinator.com/item?id=49246804)
- **Out-of-domain collapse of tuned specialists.** Google's Mobile-Actions FunctionGemma: 90.3% in-domain, 17.2% on 15 broader device-control categories. [I][D] — [arXiv 2609.25373](https://arxiv.org/abs/2609.25373)
- **Multi-turn without tuning.** FunctionGemma base 38.82% on a 6-tool multi-turn smart-home task. [C: distil-labs][D] — [card](https://huggingface.co/distil-labs/distil-home-assistant-functiongemma)
- **Parallel / multiple calls.** FunctionGemma BFCL Parallel 39, Parallel Multiple 29.5, Live Parallel Multiple 20.8. [C][D] — [card mirror](https://huggingface.co/unsloth/functiongemma-270m-it)
- **No-tool refusal.** Mixed: FunctionGemma BFCL Irrelevance 73.7 (so roughly 1 in 4 irrelevant queries still triggers a call) [C][D] — [card mirror](https://huggingface.co/unsloth/functiongemma-270m-it); but perfect restraint (2/2 prompts) in Local Agent Bench [I][D] — [README](https://raw.githubusercontent.com/MikeVeerman/tool-calling-benchmark/master/README.md). Hammer was built specifically because FC models over-call when functions are irrelevant. [C][D] — [Hammer paper](https://arxiv.org/abs/2410.04587)
- **Runtime/format friction (general local-model experience).** Reddit users report models "either not calling the right tool, or calling it correctly but then returning plain text instead of a properly formatted tool call", and different results between Ollama and LM Studio for the same model; Gemma 4 tool-calling loops and template bugs were reported in 2026. These are about larger local models, not sub-1B specifically. [I][S] — [r/LocalLLaMA mirror](https://reddit.zackpollard.pro/r/LocalLLaMA/comments/1n5mjps/what_are_your_struggles_with_toolcalling_and/nbtwu94/?context=3); [HF forum](https://discuss.huggingface.co/t/gemma-4-bug-fixes-and-research-request/176979)
- A Google AI forum post describes using FunctionGemma 270M as a router for tool calls paired with a larger Gemma for replies (router/worker split). [I][S] — [discuss.ai.google.dev](https://discuss.ai.google.dev/t/gemma-4-e2b-litert-lm-0-10-x-on-mali-gpu-patterns-from-a-structured-tool-calling-eval/143976)

### Inferences
- Failure taxonomy for sub-1B tool callers, by evidence strength:
  1. *Wrong tool under misleading wording* (keyword match beats meaning): strong independent evidence.
  2. *Argument values requiring arithmetic, relative reasoning or unit conversion*: strong anecdotal evidence across models.
  3. *Parallel / multi-call requests*: vendor's own BFCL numbers.
  4. *Out-of-distribution tools after fine-tuning*: one independent paper, large effect.
  5. *Multi-step chaining (result of call A into call B)*: Google says not heavily trained; no numbers.
  6. *Many tools in context*: plausible (BFCL "multiple" and live categories drop; Octopus/TinyAgent were designed around it) but I found no sub-1B scaling study versus tool count.
- The independent result that a general 0.6B model (Qwen3-0.6B, with thinking) beats the 270M specialist on judgment while being ~8x slower is the cleanest illustration of the core trade: tiny specialists buy latency and footprint by giving up the reasoning needed for ambiguous requests. The Local Agent Bench is, however, only 12 prompts and 3 tools, and tested FunctionGemma zero-shot, which Google explicitly says is not the intended use.
- Practical consequence for comparing with Needle and Liquid: zero-shot numbers on generic benchmarks understate what fine-tuned specialists do in-domain and overstate what they do out-of-domain; the fair comparison is post-fine-tune accuracy on the buyer's own tool set plus behaviour (refusal or confidence) off it.
